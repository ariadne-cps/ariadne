# Coupling among the source/ subdirectories — Ariadne

Baseline analysis dated September 29, 2026, branch `master`, commit `949d7e044ae65837fc02e6387701b10e7c15ddc6`.

> **Historical baseline.** The measurements and dependency grades in this document describe the baseline commit above and do **not** describe the current repository graph. As of 2026-10-04, Utility, Foundation, Numeric, Interval and Algebra form the validated standalone lower chain, and Ariadne consumes standalone Algebra. Function is the next extraction boundary. See `current-state.md` for the active structure.

## Result

At the baseline, the ten directories did not form ten independent components. The direct-include graph had **55 directed edges, 13 mutually dependent pairs, and one strongly connected component containing all ten directories**. Final classification: **9 high, 35 medium, and 11 low dependencies**.

This did not prevent using separate repositories: strong dependencies can remain explicit dependencies on versioned packages. It did mean that simply moving every directory to a repository would not create isolation. Backward cycle-closing edges had to be removed and public build dependencies and contracts had to be defined first.

The broadest relation was **function depending on algebra**: 142 include directives, 41 consuming files, 31 consuming headers, and 21 distinct algebra headers. This is not necessarily the single longest refactoring task; it is the measured reference used to calibrate the grading bands.

## Scope and method

All C++ files in the ten directories and the main/test CMake files were inspected. The measurement covers **374 files: 280 headers and 94 .cpp sources listed in CMake targets**, with **1,043 inter-directory include directives**. All headers were included even when not reached by the current build because installation exported .hpp files indiscriminately. The two aggregate headers at the root of `source/` were inspected but not treated as an eleventh component.

Seven .cpp files not listed in the targets were excluded from the counts: `algebra/dense_differential.cpp`; `dynamics/1D_pde.cpp` and `2D_pde.cpp`; `geometry/polyhedron.cpp`, `polytope.cpp`, and `zonotope.cpp`; and `numeric/mpfr_array.cpp`.

The scanner removes comments, reads quoted and angle-bracket includes, resolves relative paths and paths relative to `source/`, and counts textual directives including repetitions. Transitive dependencies are not counted as separate edges. Preprocessor conditions are not evaluated, so conditional includes are treated as potential dependencies. Test dependencies are assessed at build-configuration level and are not added to the production graph.

External dependencies such as utility/logging/threading/configuration, GMP/MPFR, and graphics backends are not graph nodes. They still matter for extracting usable packages.

This is a static analysis of includes, types, and build structure, not proof of separate compilation or linking. At the baseline the components were not compiled independently and the tests were not run as isolated component tests. Transitive includes, forward declarations, template instantiation, linked symbols, and macros may create semantic dependencies that are not represented by a direct include. A missing edge means “no direct include detected,” not “independence proven.”

Two internal includes were unresolved in the baseline tree: `function/calculus_base.hpp → calculus_interface.hpp` and `numeric/flt64.hpp → numeric/is_number.hpp`. No invented edges were added for them. `config.hpp` is generated by the build and is outside the inter-directory graph.

## Thresholds

For each relation **consumer C depends on provider P**, the analysis measures:

- I: number of include directives from files in C to P.
- F: number of distinct consuming files in C.
- H: number of distinct consuming headers in C, including `.tpl.hpp`, `.inl.hpp`, and `.decl.hpp`.
- T: number of distinct provider headers referenced.
- W = I + 2H: a heuristic that adds cost for propagation through headers.
- R = W / 204: relative score against the maximum observed relation, function ← algebra, where W = 142 + 2×31 = 204.

The coefficient and thresholds are architectural heuristics, not a standard metric or an estimate of implementation days. F, T, and percentage penetration are reported to distinguish breadth from component size.

| Initial band | Threshold relative to maximum | Operational interpretation |
|---|---|---|
| Low (B) | R < 5%, i.e. W ≤ 10 | Narrow boundary; typically a removable include, extracted declaration, localised adapter, or small shared core. |
| Medium (M) | 5% ≤ R < 25%, i.e. W 11–50 | Concrete types, algorithms, or mixed responsibilities; removing the dependency generally needs structural work. |
| High (A) | R ≥ 25%, i.e. W ≥ 51 | Strong and pervasive dependency in the mathematical model and/or public interfaces; usually keep it explicit or initially co-located. |

The final classification promotes six relations from raw B to M because their semantics matter more than their volume: **function → algebra; numeric → foundation; symbolic → foundation; solvers → geometry; symbolic → io; geometry → symbolic**. Not every edge in a cycle is automatically promoted: a low-volume edge can still close a large cycle.

Here, “decoupling” means making the boundary manageable and removing dependencies back toward higher-level implementations, possibly by moving contracts or adapters. It does not mean rewriting the provider's mathematical semantics. A low grade does not by itself make a whole directory ready for a standalone repository.

## Boundaries requiring attention

1. **foundation / numeric / symbolic.** At the baseline, numeric legitimately depended heavily on paradigms and logical contracts, while `logical.cpp` depended back on Sequence/Natural/Symbolic. That backward implementation dependency has now been removed: logical expression nodes belong to Foundation, Sequence conjunction/disjunction moved upward to numeric, and Foundation has been extracted as a standalone repository depending only on Utility. The remaining low-level issue is the numeric → symbolic expression-template dependency.

2. **algebra / function.** The dominant direction is algebra → function in graph notation, meaning function consumes algebra. The backward dependency is not cosmetic: `graded.hpp` implements `compute_procedure` and `algebra_operations.tpl.hpp` knows `TaylorSeries` and `AnalyticFunction`. These extensions should move to the function layer.

3. **geometry is not one layer.** `Interval` and `Box` are primitives required by algebra/function, while `function_set`, affine sets, and pavers depend on functions and solvers. Geometry should be split into primitive geometry, function-defined sets, and paving/optimisation algorithms before repository extraction.

4. **io / geometry.** Graphics forms a backward dependency from mathematical structures: Drawable/draw appear in boxes, grid paving, and other types, while figure/drawer code knows concrete geometry and function types. Tensor drawing has already been moved out of algebra into an IO adapter; the same principle should be applied more broadly.

5. **dynamics / hybrid.** Hybrid legitimately depends on dynamics: `HybridEnclosure` contains a `LabelledEnclosure`. The baseline reverse edges from dynamics and primitive geometry into hybrid were each caused by one unused include; both have since been removed on the decoupling branch.

6. **function / symbolic.** Formula, Procedure, and Expression cross the boundary, and generic symbolic templates are reused by lower-level code. Generic expression machinery and high-level Expression/Formula/function conversions should be separated.

## Build and tests: what the baseline lacked for separate repositories

- The ten directory targets were OBJECT libraries and `source/CMakeLists.txt` did not declare their dependency edges. The root exposed all of `source/` globally and aggregated the objects into three shared libraries.
- `ariadne-core` contained foundation, numeric, algebra, external objects, and `geometry/interval.cpp`; `ariadne-kernel` added function, geometry, solvers, io, and symbolic; `ariadne` added dynamics and hybrid. These were overlapping aggregates, not independently packaged layers with explicit dependencies.
- Only the aggregate `ariadne` target was installed/exported. `config.hpp` generated into the source tree and global include directories were additional contracts to replace with target properties.
- Numeric/algebra tests linked `ariadne-core`; function/symbolic/geometry/solvers/io linked `ariadne-kernel`; dynamics/hybrid linked `ariadne`. Therefore the baseline tests did not prove isolated linkage of individual directories.
- A `test/foundation/CMakeLists.txt` existed but was not registered from `test/CMakeLists.txt`.
- utility/logging/threading came from the submodule tree, and compatible `configuration` commits had to be coordinated.

The standalone Utility -> Foundation -> Numeric -> Interval -> Algebra chain now
provides the concrete counterexample to those baseline limitations: each
component has an explicit repository boundary, focused validation, installation
support and coordinated dependency pins, while Ariadne remains the integration
build.
